# 内存与音频链路诊断（0.6.0–0.7.2）

## 2026-10-09：0.7.2 按住对话稳定性修复

0.7.1 的现场累计诊断读到 `send_errors=5`、`send_max_ms=1144`、`receive_gap_max_ms=1063`、`playback_refills=37`（后续达到 40）；本次启动的 `wifi_disconnects=0`、`alloc_failures=0`，当时空闲堆约 61 KB、最低堆 17908 B。计数包含此前两种聊天模式，不能把全部错误归因于 PTT。服务器服务持续运行，约 202 GB 内存可用，没有本轮 OOM 或重启证据；设备 TCP RTT 现场约 235 ms，并有重传。

原播放队列只有 640 ms 容量、240 ms 预填充，覆盖不了这次观察到的约 1 秒收包间隙。设备音频发送只等待 1 秒，所用 WebSocket 组件遇到写超时会中止连接；发送错误和阻塞时长与此路径吻合，但没有故障瞬间的完整串口日志，不能断言历史断线全由同一个原因造成。两端原本已启用 TCP_NODELAY，本轮没有修改该选项。

本轮更改：

- 播放队列改存压缩 ADPCM，播放前才解码。容量从 32 个 PCM 帧增至 128 个压缩帧（640 → 2560 ms），队列内存从 30976 B 增至 32256 B，仅多 1280 B；另有约 980 B 上行合包工作区。
- PTT 每段预填充 800 ms，播放欠载后本段提高到 1200 ms。收到回复结束标记后，短回复立即排空；后续帧不足时预填充等待上限 1500 ms。正常网络下，相比旧版增加约 560 ms 首音缓冲，容量不是固定等待时间。畅聊保持 240 ms 起播及原先的积压丢旧策略。
- 协议 7 的一条上行消息合并 1–4 个独立 20 ms 包，正常连续上行的 WebSocket 消息数约降至四分之一；新增采集等待最多约 60 ms，松手先发不足 4 帧的尾包，再发 `ptt_end`。取消、换模式、重开时丢弃残留尾包。服务端保留旧协议兼容。
- 设备发送超时从 1 秒放宽至 3 秒，服务端写入超时从 2 秒放宽至 5 秒；这是阻塞容忍上限，不是每次发送固定等待。服务端输出通道仍有界，由 32 增至 128 帧。极端拥塞仍可能阻塞同步录音发送，缓冲不能消除网络故障。
- 增加 WebSocket 错误/断开次数、实际发送消息数、播放容量/目标诊断，补充服务端断开原因日志；断连清除残留的交互活动标记。

离线检查通过：25 个 Rust 测试、Clippy（warnings denied）、协议 7 的 4+4+3 帧与松手尾包顺序、旧协议兼容、模拟 Codex/媒体会话、C 端批处理/取消/欠载/短回复/时间回绕，以及 976 字节 WebSocket 封包测试。远端 Rust 1.88 release 与 ESP-IDF 5.5.3 固件构建通过。测试未调用真实 GPT。

服务端已更新至 0.7.2；设备通过 USB 写入当前 OTA0 应用分区 `0x10000`，保留 NVS，写入哈希校验通过，设备 `/api/info` 确认版本 0.7.2。固件 1584736 B，SHA-256 为 `0d1f1e8f85183b3cc564160d4b81da6950fe963bf632fd04058501693d16ff48`。该产物同时包含用户在音量任务中要求的播放增益；增益的极值、静音与恢复测试通过，实际响度仍待用户试听。

更新后运行一次 12 秒双向静音检查（沿用 probe 的畅聊播放策略，不是完整 PTT/GPT 实测）：600 帧下行全部播放，644 个上行帧合并为 161 条消息；新增发送错误、Wi-Fi/WebSocket 断连、分配失败、丢帧和播放欠载均为 0。单次发送最长 4 ms，收包间隙最大 202 ms；传输期间采样空闲堆 47460–52600 B，检查完成后 59088 B，启动累计最低堆 35564 B。检查正常结束，设备回到默认 PTT 空闲状态。上行覆盖服务端结束通知与排空等待，帧数不要求等于下行。短时检查不代表高抖动或长期真实对话已验收。

本机证据保存在 Git 忽略的 `artifacts/ptt-stability/`。原计划的更新前静音检查因设备正在交互返回 409，没有强行打断；因此本轮不存在受控的更新前后实机对比。下面保留的 0.6.0 检查是此前结果，不能作为 0.7.1 故障的同期基线。

## 2026-10-09 发现的问题

ESP32-C3 没有 PSRAM。原实现每 20 ms 发送 960 字节 PCM（24 kHz、16 bit、单声道），单向约 48 KB/s，全双工约 96 KB/s，不含网络开销。TCP 收发缓冲各 32 KiB，Wi-Fi 动态收发缓冲各 32 个；这些网络缓冲与任务、播放队列共用有限的内部 RAM。

故障时服务器服务仍在运行，Rust 进程 RSS 约 9 MB，服务器可用内存约 200 GB。设备 USB 日志显示堆只剩约 6–8 KB，网络重连超时，屏幕按键仍能响应。设备到服务器的 TCP RTT 约 340–440 ms，Wi-Fi 信号约 -41 dBm。

为排除 GPT 响应速度的影响，新增了只传输全零音频的双向网络诊断：不启动 Codex、不创建语音会话、不上传麦克风内容、不播放测试声。仅增加诊断的旧 PCM 版本（0.5.1）在约 3 秒内复现断连，USB 记录剩余堆 6004 字节。HTTP 状态接口已不可达，未取得故障瞬间的分配失败计数；因此结论是网络负载下的严重内存压力，不能据此认定某个 malloc 泄漏。

只压缩音频的中间版本已避免快速耗尽内存，但上行只有约 25 帧/秒。ESP-IDF 5.5 的 WebSocket 发送把帧头和内容拆成两次 TCP 写入，TCP_NODELAY 下占用更多小包队列项。高 RTT 使未确认小包积压，lwIP 的可写低水位会阻塞麦克风发送。这也会拖延控制消息。

## 修复

- 设备链路改为 IMA/DVI ADPCM：每 20 ms 上行 244 字节，下行 248 字节（含 epoch），约为原来四分之一；服务器内部及 GPT 媒体接口继续使用 24 kHz PCM。
- 按住说话的 16 帧预录缓存从 15360 字节降至 3904 字节。播放队列仍为 32 帧（640 ms），预缓冲仍为 12 帧（240 ms），短回复最多等待 350 ms。
- TCP 接收窗口 12 KiB、发送缓冲 16 KiB；TCP oversize 使用四分之一 MSS；Wi-Fi 动态 RX/TX 各 12 个；WebSocket 启用独立发送锁。
- `ws_send.c` 通过链接器包装 `esp_transport_ws_send_raw`，把设备的 WebSocket 帧头与内容合成一次写入。使用固定 1208 字节工作区，由 WebSocket 客户端发送锁串行保护；控制帧仍有随机掩码，部分写入按连接错误处理。其他 transport 或超过上限的帧退回原实现。升级 ESP-IDF/WebSocket 组件后必须重跑封包测试和链路诊断。
- 服务端忽略会话接收端关闭之后迟到的录音帧，避免会话结束误断开整条设备连接。
- 正常播放结束不再计入播放欠载次数。

ADPCM 是有损语音编码，CPU 需求小，不能描述为无损。实际音色与听感由用户检查。增加播放缓存会额外占内存、提高首音延迟，不能代替降低传输压力。

## 协议 5

`start`/`probe` 携带 `protocol: 5`。上行每条二进制消息为一个独立 ADPCM 包；下行前置 4 字节小端 epoch。ADPCM 包格式：

| 偏移 | 长度 | 含义 |
| --- | --- | --- |
| 0 | 2 | 本包编码之前的 predictor，i16 little endian |
| 2 | 1 | 本包编码之前的 step index，0–88 |
| 3 | 1 | 保留，必须为 0 |
| 4 | 240 | 480 个采样，先高 nibble 后低 nibble |

包携带独立解码所需的初始状态，丢弃旧 epoch 不会影响后续包。服务端继续兼容协议 1–4 的原 PCM 格式。新固件应搭配 0.6.0 或更高版本服务端。

## 诊断与回归

`GET /api/info` 的 `diagnostics` 提供当前/历史最低空闲堆、最大空闲块、分配失败次数、发送耗时/错误、收发帧数、播放欠载和 Wi-Fi RSSI。累计字段从启动开始计数；`heap_min` 不会随释放回升，比较多轮时应看当前空闲堆和累计计数差值。

设备空闲时运行：

```sh
python scripts/netcheck.py --url http://192.168.7.17 --out artifacts/diagnostics/netcheck.json
```

脚本先获取设备 nonce，再调用 `POST /api/netcheck`，双向传输 12 秒全零音频并采样状态。音频数据由固件清零，服务端验证静音；结束后等待播放队列排空，设备有 20 秒保护性停止。用户操作也会中止检查。日志不保存 nonce 或录音，输出默认在 Git 忽略的 `artifacts/` 下。检查不会调用 GPT，不代表完整真实对话已验收。

离线回归：

```sh
cargo test --locked
cargo clippy --all-targets --locked -- -D warnings
cargo build --locked
python scripts/test_session.py
python scripts/test_adpcm.py
python scripts/test_ws_send.py
```

C 编码器和 Rust 编码器使用 `scripts/fixtures/adpcm.json` 的独立 Python 3.9 `audioop` 参考向量交叉校验，涵盖静音、平滑音频、斜坡和饱和极值。封包测试覆盖短帧/扩展长度、控制帧/分片、部分写入错误和回退路径。进程回归使用模拟 Codex/媒体端，不访问 OpenAI。

本轮没有调用真实 GPT 语音；网络固有 RTT、上游会话建立与模型回答耗时仍需与用户实际体验分开评估。短时压力检查也不能排除所有长时间运行问题。

## 实机对比结果

两轮最终链路检查均为双向 12 秒静音传输，随后排空播放队列，没有重启设备：

| 项目 | 第一轮 | 第二轮 |
| --- | --- | --- |
| 传输期间每秒采样的空闲堆 | 38524–41264 B | 39260–42876 B |
| 结束后空闲堆 | 60036 B | 60048 B |
| 启动至检查完成的最低堆（非每秒采样） | 23912 B | 23912 B |
| 设备上行速率 | 约 50 帧/秒 | 约 50 帧/秒 |
| 服务端发出的下行 / 设备播放 | 600 / 600 帧 | 600 / 600 帧 |
| 分配失败 / 发送错误 / 丢帧 / 欠载 | 均为 0 | 均为 0 |
| 单帧发送最长耗时（启动累计） | 4 ms | 4 ms |

原始日志保留于本机 `artifacts/diagnostics/baseline-netcheck.json`、`baseline-usb.log`、`coalesced-netcheck-{1,2}.json`。中间版本的 `compressed-netcheck-{1,2}.json` 用于定位合包修复前的发送阻塞，不代表最终版本结果。TCP RTT 会随时变化：诊断过程中读到约 220–440 ms，因此这些是同设备、同网络路径的现场结果，并非控制变量实验。

### 仍需区分的 Wi-Fi 问题

完成两轮传输后的空闲观察又捕捉到 Wi-Fi 断连。USB 日志显示 `Wi-Fi disconnected, reason=6`，紧接着 TCP `Software caused connection abort`，随后重新关联并恢复连接。当时空闲堆约 61 KB，没有分配失败。ESP-IDF 中原因码 6 对应 `WIFI_REASON_NOT_AUTHED`（Class 2 frame from non-authenticated station），表示无线认证/关联状态异常；仅凭此码不能断定是路由器配置、AP 状态还是兼容性问题。Wi-Fi 省电已关闭，信号约 -41 dBm。

这类断线独立于已修复的音频缓冲内存压力，不能宣称所有掉线已根治。`diagnostics.wifi_disconnects` 和 `wifi_last_reason` 记录首次连网完成后的断线次数与最近原因码；USB 健康日志同时记录堆最低值、分配失败与网络发送耗时。若真实使用仍偶发整段停顿，可先用手机 2.4 GHz 热点做同设备对照，再决定是否调整现有 AP；本轮未修改路由器配置或保存的 Wi-Fi。


## 2026-10-10：0.9.1 LIVE 重连与音频突发修复

现场 0.9.0 记录到 send_max_ms=3003、receive_gap_max_ms=2572、23 次播放欠载和 183 帧丢弃。该段计数中 Wi-Fi/设备 WebSocket 未断开；服务端 LIVE 会话两次以音频队列满或对端关闭结束。离线一次性补送 120 帧（2.4 秒）可复现旧版本失败，修复后按 20 ms 节奏完整送达且维持原会话。

0.9.1 将设备 WebSocket 写入移到独立任务，媒体桥接收队列采用背压而非满队列断开；LIVE 输入使用最多 150 帧的有界队列定时发送。协议 8 下行合并 1–4 帧，最长等待 60 ms，控制消息前排空尾包。固件取消 LIVE 超过 480 ms 就大段丢帧的处理，欠载后从 240 ms 提高到 480 ms 预缓冲。VOICE 的 800/1200 ms 缓冲保持原值。

同时修复首页屏蔽静音诊断收发的问题，已有暂停会话会先停止并等确认再开始 probe。诊断脚本现在要求真实双向帧计数和完成状态，避免空跑被当成通过。

验证：隔离服务端 26 项单元测试通过，进程级离线回归（含突发输入、首页/模式切换、取消、尾帧、旧协议及 v8 合包）通过；主机音频缓冲和 WS 发送测试通过。固件写入 0x10000，esptool 哈希校验通过，设备回报 0.9.1，音量 40、音色 4 保留。

设备静音传输共执行三轮，每轮完整播放 600 帧。后两轮独立采样日志 netcheck-2/3 都验证完成：每轮新增上行 628 帧、播放 600 帧、丢帧 0、欠载 0、发送错误 0、WS/Wi-Fi 断开 0、分配失败 0；最大发送耗时 4 ms。第一轮本身完成，但其 24 秒采样窗口与第二轮重叠，脚本正确标记该窗口不可用于独立完成判定；以第二、三轮作为独立结果。

这些是同设备不同时间的现场观察，Wi-Fi 信号和链路状态会变化，不能把数值差异全归因于补丁；静音 probe 不包含真实模型或听感验收。用户仍需实际试听 VOICE/LIVE。

证据位于 `artifacts/audio-0.9.1/`；部署快照与清单见 `release/` 和 `manifest.json`。本次发布沿用现网 codex.rs，未包含工作区同时进行的上下文功能改动。


## 2026-10-10：0.9.2 音色应用确认

用户反馈名称已改变、听感未改变。检查确认旧路径已经保存音色并重建会话，也传入了 Codex start 的 voice；因此不能把问题简单归因为 NVS 未保存。新增显式媒体通道音色配置和确认门控，避免把 WebRTC 已连接当成音色已应用。原始 session.started 只返回 id/status/expires_at，不返回实际音色；该限制使旧路径的生效状态无法验证。

实际订阅通道接受开口前的音色 session.update 并返回 session.updated。0.9.2 等此确认后才开放音频，再向设备回传选定音色；设备将它与保存值比较，不匹配时停止会话并显示失败。这里确认的是配置命令被接受，不是由上游返回的声纹鉴定，不能据此声称已客观证明所有音色的听感。

验证：29 项 Rust 测试、进程级会话回归（包含切声后的 ready 音色）、VoiceSetup 拒绝/超时/不匹配/重复确认/关闭测试通过。独立真实会话 Cove/Breeze 配置确认通过，Juniper/Ember 分别产生 3.86/4.42 秒回复音频。设备刷入 0.9.2 并校验哈希后，通过设置 HTTP 入口实际从 Ember 切到 Juniper 再切回 Ember：每次保存值、服务端确认、设备 active_voice 一致，测试未开放麦克风，音量保持 40。

证据位于 `artifacts/voice-0.9.2/`，包含 `device-voice-results.json`、构建/刷写/回归日志；测试保留了当前现网的上下文模块。真实听感待用户复测。

## 2026-10-10：0.10.1 两种模式统一 500 ms 预缓冲

按用户要求，LIVE 和 VOICE（chat/PTT）的首次起播、欠载后恢复均改为 25 个 20 ms 帧，即 500 ms。此前 LIVE 为 240/480 ms，VOICE 为 800/1200 ms。队列容量仍为 128 帧／2.56 秒，不增加播放队列内存。短回复收到结束标记仍可提前播放；缺少后续帧且没有结束标记时，LIVE 的 650 ms、VOICE 的 1500 ms 饥饿等待上限保留。这些上限不是新的预缓冲目标。

主机音频回归检查两种模式在 480 ms 不起播、500 ms 起播，欠载后同样重新积累 500 ms，并覆盖短回复、计时回绕、代次重置、恢复突发按序播放和上传尾包。29 项 Rust 单元测试、AudioWorklet、音色握手、完整离线进程回归通过。ESP-IDF 5.5.3 构建成功，镜像 1,604,000 bytes；构建输入校验、烧录和检查证据保存在 `artifacts/audio-0.10.1/`。

### 另外确认的聊天稳定性问题

1. **LIVE 积压缺少追赶策略，已离线复现。** 当前实时音频以每 20 ms 一帧的固定速度送入媒体桥。一次性补送 100 帧（2 秒），随后持续 8 秒按正常速度送入新音频，四次采样的待处理音频均为约 2020 ms；新输入持续到达时，旧积压没有消退。再补送 2 秒突发会超过 150 帧上限，返回可重试的网络错误并结束语音会话。复现使用真实 Rust 服务和假 Codex／媒体端，不访问模型；结果见 `live-backlog-result.json`。此前“2.4 秒突发完整送达”回归只验证突发后停止新增输入的排空，没有覆盖持续到达。500 ms 的设备下行预缓冲不改变这个上行问题。后续应设计有界延迟恢复策略，优先评估静音追赶，避免盲目丢弃正在说的话。
2. **设备采音与网络发送耦合，代码确认。** `microphone_task` 持有 `send_lock` 时同步发送音频，发送超时参数为 3000 ms；同一锁也服务控制消息。弱网长时间阻塞可阻止及时读取后续麦克风采样，并延迟控制发送。BSP I2S DMA 仅约 60 ms，播放端增加缓冲不能保护这些上行采样。后续优先拆分采集与发送，使用固定容量队列，并为结束、取消、切换保证明确的顺序与响应边界。
3. **普通问答仍用静音划分回复段，代码确认、听感待验收。** 输出连续约 650 ms 没有有效声音就标记播放段结束，下一段使用新代次并重新预缓冲。长回答中的自然停顿可能因此叠加分段等待；需要结合真实长句、语气停顿和下游排空时间验证，不能仅将等待归因于模型。
4. **自然插话与主动停止的语义不同。** LIVE 自然插话交给上游模型处理，本地不据此清空队列；主动按键停止才清理旧播放和抑制迟到帧。扩大预缓冲会增加可能残留的已排队旧语音，真实插话验收需单独观察它；不能只用主动停止的离线通过代替。

本次固件仅调整播放缓冲；以上服务端积压和采音发送架构问题作为后续改进项记录，不声称已经修复。静音传输验证也不能代替真实对话、长时间使用和主观听感验收。

实机发布验证：先备份完整 8 MB Flash，读取真实分区表和 OTA CRC 确认当前槽为 ota_0，只写入 0x10000 应用并通过哈希校验。首次 USB RTS 复位未退出刷机 stub，补做 esptool watchdog reset 后设备正常启动并读回 0.10.1。原音量、音色、亮度、息屏、空闲、模式和 Wi-Fi 列表保留。两轮独立 12 秒双向静音传输分别上传 644／648 帧、完整播放 600／600 帧；两轮新增丢帧、欠载、发送错误、WS/Wi-Fi 断连、分配失败均为 0，最大发送耗时 5 ms，采样播放目标始终为 500 ms。结束后回到 NAVIGATION，麦克风上传关闭，服务器确认设备连接。证据见 manifest.json、netcheck-1/2.json 和 after-validation.json；没有发起真实模型语音或进行主观听感验收。

## 0.10.3 — 发送背压与重连去重

修正固件的共享发送路径，VOICE 与 LIVE 的首播和欠载重缓冲仍为 25 帧／500 ms，播放容量仍为 128 帧／2.56 s。

- 麦克风采样／ADPCM 编码与 WebSocket 写入拆成独立任务。48 帧固定采集队列占约 12 KiB，可容纳 960 ms 短时积压；它是上行容量，不额外等待填满，不改变 500 ms 播放目标。采音不再持有网络发送锁。
- 上行发送仍按四帧合包。PTT 结束先关闭采集并等待已准入帧入队，然后发送剩余帧、部分合包和结束消息。取消、停止、模式切换用采集代次使旧帧失效。极端拥塞填满采集队列时，LIVE 淘汰最旧输入并记录计数；VOICE 取消这次录音并提示 NETWORK SLOW，不把截断输入当正常问句提交，也不因此重建连接。
- 原 WS 包装器先等 select 可写，再单次 write；lwIP 可写条件基于发送字节和 pbuf 队列的低水位，并不等于当前小帧能否写入。新发送器先使用非阻塞 send，EAGAIN／EINTR 在同一个总期限内重试；部分写入只补剩余字节，不重发帧头。真实连接错误或耗尽期限才交给 WS 客户端中止连接。超时上限仍为 3000 ms，没有用加长超时掩盖问题。
- 发送失败、断连与 idle 通知共享幂等恢复状态，同一次失败只累计一次重试；异步故障带会话代次，过期故障不终止后来建立的会话。
- 增加 capture_queued／capture_dropped／capture_overruns 和采音、播放峰值诊断。USB 的 voice／record／send／cancel／home 调用相同控制路径，trace on/off 仅在明确开启时打印控制消息。真实测试不使用静音 probe。

主机回归：scripts/test_ws_send.py 直接编译实际发送器，覆盖数据／控制／分片帧、部分写入、450 ms 暂时不可写、EINTR、单一总期限和永久错误；scripts/test_capture_transport.py 编译实际控制边界与 retry 函数，覆盖尾帧先于结束、取消清空、代次隔离、发送失败不提交结束、故障去重；test_audio_transport.c 验证两模式 500 ms。

调查边界：旧日志记录过约 3005 ms 发送超时与设备主动断连。本次新增诊断后，修复前的真实问答基线也没有复现该故障，因此不能把上述低水位或部分写入风险宣称为历史故障唯一已证实触发器。实机回归结果另记，使用各测试前后的计数差值，避免把刷机期间旧连接清理误计为聊天故障。
