# 架构与音频协议

## 运行链路

```text
ESP32-C3 / ES8311
  ⇄ WebSocket / 音频协议 8
Rust Axum / Tokio 服务
  ⇄ 本机 Chromium AudioWorklet / WebRTC
GPT-Live
  ⇄ Codex app-server / 原生工具与订阅登录
```

设备主动连接服务器，Mac 不承担在线语音中转。服务器同时接纳一个设备。Chromium 只负责媒体协商、编解码和音频时钟；账号、临时 thread 和工具由 Codex 管理。Codex 接入使用实验性 v3 通道，升级运行依赖时需重新核对适配。

## 会话与收音

首页不收音、不播放。VOICE 进入即开始录音，边录边传，按 OK 发送；模型提前生成的回复在服务器缓存，发送后才按序播放。最长录音 60 秒，有界回复缓冲防止无限积压。

LIVE 保持双向媒体流，不等待静音或播放排空才开放输入。短按 OK 主动停止回复；收到非空用户转写时也会清理设备旧播放，抑制旧助手尾音，直到新一轮助手输出。自然插话依赖上游识别与网络传输，没有新增 AEC。

首页返回暂停现有会话，重新进入可以复用上下文。断线、闲置超时、最长 30 分钟和明确重置结束会话。保存不同音色时重建会话，收到匹配的 session.updated 后才报告 ready；拒绝、超时或不匹配均报错。

设备桥连接后，服务器预备账号与临时 thread，不开启实时语音、不上传麦克风、不提前选择音色。开始对话时复用准备结果，并行准备浏览器 SDP 和后端；首次开机尚未准备完、WebRTC 与音色确认仍有等待。

## 音频格式与队列

| 链路 | 格式与限制 |
| --- | --- |
| 采样 / 媒体桥 | 24 kHz、单声道 PCM s16le；20 ms / 480 采样 / 960 B |
| 设备上行 | IMA ADPCM，每帧 244 B；每条 WebSocket 消息 1–4 帧 |
| 设备下行 | 每帧 248 B，含独立 4 B epoch；每条消息 1–4 帧 |
| 采音发送队列 | 48 帧；采集与网络发送分任务运行 |
| 设备播放队列 | 128 帧压缩音频 / 2.56 秒 |
| 起播 / 欠载恢复 | 25 帧 / 500 ms 目标；短回复收到结束标记可提前播放 |
| 不足目标的等待上限 | VOICE 1500 ms；LIVE 650 ms |
| LIVE 服务端上行 | 有界 3 秒队列，按 20 ms 节拍送入媒体桥 |

上下行合包最长新增等待 60 ms，控制消息前先排空尾包。500 ms 是缓冲目标，2.56 秒是容量，均不能直接等同每次响应的固定延迟。

WebSocket 部分写入继续补齐剩余字节；临时不可写在同一超时期限重试，同一次故障只安排一次恢复。极端拥塞下 LIVE 可丢弃旧输入，VOICE 超限取消录音；旧 epoch 的迟到音频不会重新播放。设备发送超时 3 秒、服务端写入超时 5 秒。服务器仍支持旧协议，离线会话回归保留兼容检查；现役设备使用协议 8。

## 资源与恢复

设备 LVGL 静态池 24 KiB，字体与字标在 Flash。TCP 接收窗口 12 KiB、发送缓冲 16 KiB，启用 TCP_NODELAY。暂时语音错误按 2/4/8 秒退避，连续失败后提示手动重试；登录或额度问题不循环自动重试。

诊断通过设备 /api/info 的 diagnostics 查看：发送耗时与错误、采音丢弃、播放队列、heap、音色确认与麦克风状态。检查前区分只读信息和会实际发送数据的 netcheck / USB 命令，见 [测试说明](testing.md)。

OTA 与网页网络维护共用互斥状态，维护期间忽略语音控制与迟到状态。固件下载只使用当前 VOICE_URL 对应服务器，验证发布签名与镜像 SHA-256 后切换启动槽。详细发布步骤见 [配网与 OTA](wifi-ota.md)。
