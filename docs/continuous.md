# 连续对话协议 v2

第一阶段现场验证通过；第二阶段的交互目标是一次按键开启、之后轮流听说。服务端是 Rust，ESP32-C3 使用 ESP-IDF C。没有新增长期记忆、唤醒词、账号管理或数据库。

## 正常轮换

设备发送 `{"type":"start","protocol":2,"mode":"continuous","idle_seconds":180}`。服务保留同一个 Codex 临时 thread、WebRTC 连接和媒体进程，直至用户结束、超时或断连。

1. 服务依次发送 `status:ready` 和 `listen(epoch)`；设备打开麦克风上行。
2. 收到模型非静音输出，服务关掉媒体输入队列，发送 `playback_begin(epoch)` 和该代号的音频；设备关闭麦克风上行并开始预缓冲。
3. 连续 650 ms 没有非静音输出，服务发送 `playback_end(epoch)`。
4. 设备播空对应队列，继续给 I2S 写静音至少 180 ms，发送 `playback_drained(epoch)`。
5. 服务只接受当前代号的排空确认，重新发 `listen(epoch)`。设备确认距最后一次播放至少 180 ms 后开始上传；已经满足保护时间时立即恢复，不再额外等待。

任何后续非静音输出都能重新进入播放。如果它发生在排空确认到达前，服务会换代号，旧确认不再打开麦克风。因此不会因一条迟到的确认在扬声器仍播放时误开收音。

音频输入：960 bytes PCM s16le mono 24 kHz。音频输出：`u32 little-endian epoch` + 960 bytes PCM。所有控制均为 JSON Text WebSocket 消息。输入仍持续以静音维持浏览器 WebRTC 时钟；播放时不向语音服务送入设备扬声器的回声。

## 按键打断

设备按 OK 后立即停止出声、清空本地队列、拒绝后续旧音频，发送 `interrupt`。服务更新代号，回 `clear(epoch)`，恢复用户输入，并通过已部署 Codex 0.159.2 的 `thread/realtime/appendText`、`role:developer` 发送应用编写的停止上一回复指令。不是把设备端任意文字当作 developer 指令。

上游未暴露确定性取消媒体的 RPC，因此远端停止属于指令引导；本地静音与代号丢弃是确定的。服务还要求旧输出出现至少 200 ms 静音边界，且收到新的用户话音/转写事件，才放行新的输出，避免迟到旧音频重新响起。新的用户轮次与静音边界可以按任意顺序到达。

若按键打断后不说话，设备继续等待；不会主动朗读打断指令。断网恢复会创建新会话并清空屏幕旧字幕，正常打断保留本次会话上下文。

## 缓冲与资源

设备播放队列 32 × 20 ms，预填充 12 帧。短回答不满 12 帧时，350 ms 超时或收到结束提示即可播放。队列溢出仅丢最老一帧，计入 `dropped`；服务端发送队列满则结束连接，避免无限延迟。

屏幕只保留上一句用户和助手字幕，各最多 180 个 Unicode 字符。没有录音或转写持久化。设置存在 NVS；字体常驻 Flash。空闲统计依据用户声音/转写和助手非静音输出，不由上传的静音帧续期。

## 验证边界

Rust 单元测试覆盖排空确认、旧代号、暂停恢复、打断与新用户事件顺序；JavaScript 离线检查覆盖 AudioWorklet 的清空、容量上限和 20 ms PCM 分帧。它们不能证明真机的中文识别率、远端停止时机或实际听感。

连续多轮、打断后立即接下一句、背景噪声下的闲置结束、断网恢复、手机设置与实际 OTA，由用户按其要求现场体验。长停顿如何区分一句结束和句中停顿，受上游音频行为影响；当前使用明确的半双工切换，并未实现自动语音打断或 AEC。
