# mic-on 语音协议 v7 与多级设置

ESP32-C3 保持 ESP-IDF C，业务服务为 Rust。开机显示首页，提供语音问答和自由对话；不引入唤醒词、长期记忆和文件管理。

## 启动与设置

设备发送：

```json
{"type":"start","protocol":7,"mode":"ptt","voice":"cove","duplex":1,"idle_seconds":180}
```

- `mode`：`ptt` 或 `continuous`；自由对话始终全双工。`duplex` 仅保留旧字段兼容，不再关闭自由对话输入。
- `voice`：cove、juniper、maple、spruce、ember、vale、breeze、arbor、sol。
- 0.7.3 移除 `pace`、`reply_length`、`language`，服务器忽略旧客户端发送的这些字段，不影响会话启动。语速、回答长短和语言直接由用户在聊天中提出，不设固定系统偏好。
- 声音设置只保留 Codex 原生音色参数，在会话启动时读取。0.7.6 起，设备菜单或手机设置页成功保存不同音色会自动 stop/stopped/start，清空旧上下文并以当前聊天模式启动新音色；相同音色、取消和保存失败不重开。提示词仅描述语音终端能力与等待用户开口，不限定语言、语速、回复长度、闲聊或推理方式。
- 偏好存储在 `prefs_v4`；从 v3/v2 精确读取旧四整数布局，保留音量、亮度和超时。旧 `mode` 字段保留布局兼容但不用于启动，开机进入首页，首次默认选中语音问答，模式不落盘。Wi-Fi NVS 不变。0.7.3 将原三个风格整数保留为无效占位，`prefs_v4` 仍为 40 字节，保存时清零占位，不重置音色、音量或设备偏好。

当前订阅桥使用 Codex CLI 0.159.2。`thread/realtime/listVoices` 返回 v1/v2 两组；该版本 `core/src/realtime_conversation.rs` 的 `validate_realtime_voice` 将 **V3 映射到 V1**，不能把公开 API 的音色直接填入。来源：[对应版本实现](https://github.com/openai/codex/blob/rust-v0.159.2/codex-rs/core/src/realtime_conversation.rs)。

协议 v7 的每条上行消息含 1–4 个独立的 244 bytes ADPCM 包（20–80 ms），服务端先校验完整批次、再按原顺序拆成 20 ms 帧，点击发送时先发送最后不足 4 帧的尾包，再发送 `ptt_end`。v5/v6 仍每条消息一个包。下行每帧前置 `u32 little-endian epoch`，共 248 bytes；协议 v8 每条下行消息合并 1–4 个完整帧（248–992 bytes），最长合包等待 60 ms，控制消息前发送尾包，v5–v7 仍单帧下行。媒体桥内部继续使用 960 bytes PCM（24 kHz、s16le、mono、20 ms）。旧协议 v2/v3/v4 为 960/964 bytes PCM。过期音频丢弃。旧协议 1 的 PTT 脚本继续接收未加代号的 960 字节音频和转写。协议 1/3 继续兼容原先松手后才重放输入的行为。

## 语音问答（PTT 传输）

1. 从首页进入时预先建立 PTT 会话；短按 OK 释放后开始录音，发送 `ptt_start`，再按一次停止收音并发送 `ptt_end`。不再使用按住判断与本地预录缓存。接通期间也可以上传。
2. 服务器入口最多 3008 条消息。媒体就绪后，`PushToTalk` 按 20 ms 时钟持续向 AudioWorklet 送入录音，不等点击发送。丢失时钟不累加逐帧延迟。
3. 模型在录音期间提前产生的音频进入服务器 `ReplyBuffer`，设备此时不收到播放帧。若输入静音后再次说话，丢弃尚未播出的早期回复并引导模型停止旧回答。
4. 点击发送先排空上行尾包，再发送 `ptt_end`；未发送的少量输入继续排空，再留 600 ms 给 worklet 尾部。`submitted` 表示本次输入已提交。缓存回复按 20 ms 时钟输出，保留开头；不同播放代号之间等待设备排空确认，避免队列溢出或尾音丢失。发送后麦克风保持关闭。
5. 思考或回复时短按 OK 发送 `cancel`，清空旧输入与回复，保留会话。下一次短按开始新的输入；长按 OK 则取消未提交的录音并返回首页，不发送 `ptt_end`。结束和断线销毁内存缓存，没有音频落盘。

一轮最多 3000 个输入帧，即 60 秒，计数包括已发送的帧；固件达到此值自动发送，服务器拒绝超限。输入积压和回复缓冲各有 3000 帧上限，单份约 2.88 MB，在服务器分配。Live 此通道没有手动 commit/response-create，PTT 的发送动作控制的是应用播放，不保证模型到点击发送才开始推理。它消除了旧版完整录音重放的线性等待，首次接通和上游响应耗时仍然存在。

日志仅记录耗时／数量：媒体建立耗时、松手时输入与回复积压、首个模型音频、首个下发音频，以及设备的 `release_to_speaker_ms`。不会记录录音或转写。服务器下发时间不含设备起播缓冲；0.10.1 起，VOICE（PTT/chat）和 LIVE 的首次起播、欠载恢复均以 25 帧／500 ms 为目标，短回复带结束标记则直接排空。容量 2.56 秒不代表每次等待 2.56 秒；未结束但后续帧不足时，VOICE 最多等待 1500 ms、LIVE 最多等待 650 ms 后播放已有帧。

## 持续双向自由对话

1. status:ready 后发 listen，打开输入。麦克风和扬声器独立，不因对方说话切换收音权限。
2. 持续转发模型音轨，含静音；一次播放流只建立一个 epoch。不使用静音、字幕结束或 playback_drained 决定何时接受用户输入。
3. 用户增量转写仅更新内部会话状态，不自动清理音频，也不向模型追加停止指令。自然插话由 GPT-Live 根据连续音轨处理。
4. 输出能量和 650 ms 计时仅用于屏幕活动状态，不控制自由对话输入或输出。用户已说话且模型尚未回复时保留交互活动状态，短按 OK 仍可停止。
5. 返回首页先关闭设备收音与下行接收、清空播放队列，再发送 `pause` 和 `cancel`，取消本轮且保持输入关闭。首页和设置期间丢弃迟到的下行帧。重新进入任一对话模式发送 `mode`，解除暂停并保留既有 WebRTC 和 Codex thread；首页停留期间模型输入端的音频时钟仍输出静音。
6. 设备使用固定 128 帧压缩队列，两种模式均以 25 帧／500 ms 预缓冲起播和恢复。网络恢复后到达的音频按序播放，只有 128 帧队列真正满时才淘汰最旧帧；不再因积压超过半秒大段丢弃。诊断记录丢帧和入队到播放的最大年龄；不是网络端到端延迟。

## 主动停止与模式切换

短按停止发送 `cancel`。服务器清空 PTT 输入/回复缓存、递增播放 epoch，设备清旧队列；不关闭 Codex thread。语音问答等下一次短按；自由对话持续收音，但抑制旧输出，等新的用户输入及相应助手增量转写恢复。旧助手的最后一条完成事件不能单独恢复声音。主动停止向上游发送固定的应用控制指令；其完成不等同于音频已停止或上下文精确截断。

`mode:continuous` 和 `mode:ptt` 在同一 thread 内切换。用户长按 OK 返回首页，再选择任一对话模式。切模式清理旧播放，下一次明确的新输入恢复输出。更换音色会自动新开对话并清空上下文；仅切换聊天模式时，聊天中的风格要求随本次会话上下文保留。

旧的 200 ms 静音隔离及 playback_drained 轮次控制只用于兼容 PTT 输出，不再参与自由对话。客户端消耗 v3 的 input_transcript.added、output_transcript.added 和 turn.done，空转写完成事件也要结算归属；转写不显示、不存盘。

新对话先 stop，等待服务发 **stopped** 后再 start。stopped 在旧任务终止后发出，即使旧任务已经自然结束/不存在也会回复，避免用户在待机新建时无限等待。创建全新临时 Codex thread、浏览器和 WebRTC；不注入旧转写/history。配置切换不伪装成清空屏幕。

## 按键与菜单

- 首页：语音问答 / 自由对话 / 设置。上下选择，短按 OK 进入，返回时保留对应入口的焦点。
- 语音问答：短按 OK 开始／发送，思考或播放中短按停止。自由对话：短按停止回复，空闲直接开口。断线或会话结束后短按重试。
- 两种对话页上／下键调音量；按下立即调整，长按 500 ms 后每 150 ms 调整 5，松手保存一次。
- 全局长按 OK 600 ms 返回：对话页到首页，设置逐级返回；首页长按不产生其他动作。一次手势消费后，须全部松手才能开始下一次操作，防止返回后误进入首页选项。
- 设置提供音色 / 设备设置 / 网络设置 / 重置上下文 / 返回首页。确认清空或进入维护操作仍需要独立确认，返回不执行确认动作。
- ADC 每 10 ms 采样，3 次稳定后提交状态。可辨识的组合键和手势中途混入的无效输入不触发菜单或录音。电源键由硬件处理。

## 检查边界

Rust 测试覆盖播放代号、打断顺序、新旧 PTT 输入策略、60 秒总量上限、有界回复及跨代号排空。`scripts/test_session.py` 启动真实 Rust 服务与假 Codex/媒体进程，验证启动录音、新协议边录边传、松手前不播放、完整回复、同一 thread 切模式、音色/指令、新建上下文、全双工、菜单暂停/恢复和停止确认。C 主机回归覆盖按键绑定和菜单返回路径。测试不调用真实订阅，不能证明实际模型响应时间、实机听感或全双工效果。
